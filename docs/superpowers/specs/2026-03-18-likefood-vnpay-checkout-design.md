# LikeFood VNPay Checkout 4-Step Design

Date: 2026-03-18
Owner: Codex + User
Status: Draft ready for review

## 1. Summary

Implement VNPay payment flow for LikeFood by adapting the proven pattern from `Book_Store` and integrating it into both backend and frontend.

Checkout will be expanded from 3 steps to 4 steps:
1. Cart Review
2. Shipping Information
3. Payment Selection + Confirm
4. Order Completed

The key UX rule requested by user:
- Even if VNPay is not completed (user closes VNPay page/tab), order still goes to Step 4 (order placement success).
- Payment state remains truthful in backend and UI (`FAILED` by default for VNPay method until successful callback).

## 2. User-Approved Decisions

1. Only `BANK_TRANSFER` uses VNPay.
2. `COD` remains existing flow.
3. Checkout becomes 4-step flow with payment method step.
4. For VNPay orders, default payment status is `FAILED` after order creation.
5. Step 4 always represents order placement success, not payment success.
6. Step 4 must show payment status clearly:
   - `FAILED` or not completed: order success + payment not completed message.
   - `PAID`: order success + payment success message.

## 3. Current State and Gap Analysis

## 3.1 Book_Store reference flow (source of truth pattern)

From `Book_Store`:
- `OrderController#createOrder` creates order and generates VNPay URL for banking payments.
- VNPay URL generated by `VNPayService` using signed parameters and return URL.
- Payment callback update flow exists (`/order/update_payment`) and updates stored order by `paymentRef`.
- `paymentRef` is generated and tied to order.

## 3.2 LikeFood current flow

Backend:
- Orders are created via `POST /orders/me`.
- `PaymentMethod` exists (`COD`, `BANK_TRANSFER`, `E_WALLET`), but no VNPay flow.
- `PaymentStatus` exists (`PENDING`, `PAID`, `FAILED`).
- No `paymentRef` field and no VNPay callback endpoints.

Frontend:
- Checkout is currently 3 steps.
- No payment method selection step.
- `submitOrder` always sends `paymentMethod: 'COD'`.
- No VNPay callback route/page.

## 4. Target Architecture

## 4.1 Backend architecture

Add VNPay integration module under order/payment domain:
- `VNPayService` for URL generation + signature logic + request IP extraction.
- Extend order data model to include VNPay reference fields.
- Extend order controller/service to return a payment action payload for frontend.
- Add callback endpoint(s) for VNPay return handling.

## 4.2 Frontend architecture

- Checkout UI becomes 4-step state machine.
- Step 3 creates order and branches by payment method.
- VNPay opens from backend-provided URL.
- Step 4 always renders order-complete state with payment sub-status.
- Add dedicated frontend route for VNPay return redirect handling.

## 5. Detailed Requirements

## 5.1 Backend requirements

### Data model changes (`Order`)

Add fields:
- `paymentRef` (string, unique nullable)
- optional `paymentGateway` (string/enum, value `VNPAY` when applicable)

Keep existing fields:
- `paymentMethod`
- `paymentStatus`
- `paidAt`

### New/updated backend behavior

1. `POST /orders/me` behavior:
- If `paymentMethod = COD`:
  - Keep current logic.
  - Payment status remains current behavior (`PENDING` today).
  - Response: order payload with `paymentRequired = false`.

- If `paymentMethod = BANK_TRANSFER`:
  - Generate `paymentRef` (UUID, no dashes similar to `Book_Store`).
  - Set `paymentStatus = FAILED` by default (user request).
  - Save order.
  - Build VNPay URL from saved order total + paymentRef + client IP.
  - Response: order payload with `paymentRequired = true`, `paymentProvider = VNPAY`, `paymentUrl`.

2. VNPay return/callback endpoint:
- Verify signature and query values.
- Locate order by `paymentRef` (`vnp_TxnRef`).
- If VNPay response code is `00` and signature is valid:
  - Set `paymentStatus = PAID`.
  - Set `paidAt = now`.
  - Optionally set `paymentMethod = BANK_TRANSFER` (already set).
- Otherwise keep `FAILED`.
- Redirect user to frontend callback route with normalized query params.

3. Retry endpoint (recommended):
- `POST /orders/me/{orderId}/payment/vnpay/retry`
- For logged-in owner of the order only.
- If order payment status is not `PAID`, generate new VNPay URL using existing `paymentRef`.

### Configuration

Add in `application.yml` / env:
- `likefood.vnpay.tmn-code`
- `likefood.vnpay.hash-secret`
- `likefood.vnpay.pay-url`
- `likefood.vnpay.return-url` (backend endpoint)
- `likefood.vnpay.frontend-return-url` (frontend route to redirect after backend processes callback)

### Security and routing

Allow public access for VNPay return endpoint(s):
- `GET /payments/vnpay/return`
- optional `GET /payments/vnpay/ipn`

All order create/retry actions remain authenticated.

## 5.2 Frontend requirements

### Checkout flow update

Change `Checkout` flow state:
- Step 1: cart
- Step 2: shipping form
- Step 3: payment method + submit
- Step 4: complete

### Step 3 payment UX

- Show choices:
  - `COD`
  - `BANK_TRANSFER (VNPay)`
- On confirm:
  - Call create order API with selected payment method.
  - If COD: go Step 4.
  - If BANK_TRANSFER:
    - open `paymentUrl` in new tab
    - go Step 4 immediately in current tab

### Step 4 success UX (user-approved)

Always show order success block.

Additionally show payment badge/message:
- `PAID`: "Thanh toán VNPay thành công"
- `FAILED`/not completed: "Đơn đã tạo thành công, thanh toán chưa hoàn tất"

Provide CTA:
- View Orders
- Retry VNPay payment (if not `PAID`)

### VNPay return route

Add route page e.g. `/vnpay/return-url`:
- Read normalized status from query.
- Optionally fetch latest order status.
- Navigate user to `/checkout` Step 4 or `/myorders` with success message.

### Persistence

Store lightweight checkout completion state:
- `lastCheckoutOrderId`
- `lastCheckoutPaymentMethod`
- `lastCheckoutPaymentStatus`

Use sessionStorage to survive reload and keep Step 4 visible.

## 6. API Contract Proposal

## 6.1 Create order response shape (extended)

Current endpoint: `POST /orders/me`

Response body wrapped by current `RestResponse` wrapper; `data` should include:
- `order`: existing `OrderResponse`
- `paymentRequired`: boolean
- `paymentProvider`: `VNPAY` or `null`
- `paymentUrl`: string or `null`

This avoids breaking old consumers while enabling payment branching.

## 6.2 Retry VNPay response

`POST /orders/me/{orderId}/payment/vnpay/retry`

`data`:
- `orderId`
- `paymentUrl`
- `paymentRef`

## 7. Error Handling and Edge Cases

1. VNPay tab blocked by browser popup:
- Still keep order created.
- Step 4 rendered.
- Show retry payment button.

2. User closes VNPay tab:
- Step 4 stays success.
- Payment remains `FAILED`.

3. Callback delayed:
- Initial Step 4 may show not completed.
- Status updates later from orders list/refresh.

4. Signature invalid or malformed callback:
- Do not mark as paid.
- Log warning with paymentRef.

5. Duplicate callback:
- Idempotent update: once paid, keep paid.

## 8. Testing Strategy

Backend tests:
1. Create COD order -> `paymentRequired=false`.
2. Create BANK_TRANSFER order -> `FAILED` default + `paymentUrl` exists.
3. Valid VNPay callback code `00` -> status becomes `PAID` and `paidAt` set.
4. Invalid callback signature/code -> remains `FAILED`.

Frontend tests (manual/integration):
1. 4-step navigation works.
2. COD reaches Step 4 without payment URL.
3. VNPay opens new tab and Step 4 appears immediately.
4. VNPay abandoned -> Step 4 still success + payment not completed notice.
5. Retry button opens VNPay URL again.

## 9. Rollout Plan

1. Backend first (model + API + callback).
2. Frontend 4-step UI and VNPay route.
3. End-to-end test with VNPay sandbox.
4. Optional admin visibility: show paymentRef/payment gateway in order detail.

## 10. Non-Goals

- No change to shipping fee calculation logic.
- No integration for `E_WALLET` in this scope.
- No automatic order cancellation on payment timeout in this phase.

## 11. Open Notes

- The user intentionally requested default `FAILED` for VNPay creation to preserve Step 4 order completion UX even if payment is abandoned.
- This design separates "Order placement success" from "Payment success" explicitly in both data and UI.
